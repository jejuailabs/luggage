# 09. 검증·배포·운영·PWA·위챗

연결: [메인](../AGENTS.md), [구조](04-architecture-integrations.md), [권한](05-data-auth-security.md)

## 1. 완료의 정의

화면 구현, mock 업무 검증, sandbox 공급사 연동, live 운영 연결, 미니프로그램 제출, 미니프로그램 심사 상태를 별도로 기록한다. API 키가 없다는 이유로 기능 개발을 중단하지 않지만 mock 성공을 실제 결제·배송 성공으로 보고하지 않는다.

각 작업의 완료 조건:

1. 관련 기능 ID와 수용 조건을 충족한다.
2. 입력·실패·빈 상태·권한 없는 상태를 처리한다.
3. 데이터 변경은 마이그레이션과 재현 가능한 시드로 정의한다.
4. 중요한 상태·금액·권한은 의미 있는 자동 테스트가 있다.
5. UI는 언어·테마·기기 조건을 확인한다.
6. 관련 검증 결과와 미검증 범위를 메인 진행 기록에 남긴다.

## 2. 테스트 층과 최소 범위

| 층 | 검증 대상 | 예시 |
|---|---|---|
| 도메인 | 가격·상태·시간·배분 | 할인 반올림, 마감, 허용 전이 |
| DB | RLS·제약·트랜잭션·동시성 | 타인 주문 차단, 마지막 슬롯 |
| API | 인증·DTO·멱등·외부 실패 | 위조 가격, 재전송, timeout |
| E2E | 실제 사용자 업무 흐름 | 예약→결제→수거→인계→지원 |
| 기기 | 브라우저·카메라·결제 복귀 | 위챗 웹뷰, iOS, Android |
| 운영 | 백업·복구·재시도·롤백 | worker 중단, 파일 복구 |

단순 문구·스타일 변경에 구현과 같은 내용을 복제한 테스트를 추가하지 않는다. 가격·권한·결제·수용량·수령 코드는 반드시 실패 경로를 포함한다.

## 3. 대표 E2E 시나리오

| ID | 흐름 | 핵심 확인 |
|---|---|---|
| E2E-01 | 간체 guest, 호텔→공항, 짐 2개 | 한국 번호 없이 예약, 서버 결제 확인 |
| E2E-02 | 결제 완료 후 창 닫기·다른 기기 복구 | 소유 검증, 주문 유지 |
| E2E-03 | 호텔 보관→기사 수거→공항 인계 | QR·사진·수량·수령 코드 |
| E2E-04 | 일부 짐 누락·고객 지각 | 부분 상태·지원, 허위 완료 없음 |
| E2E-05 | 결제 전 취소·결제 후 취소·수거 후 취소 | 용량·환불·반환 책임 분리 |
| E2E-06 | 호텔 A·B, 기사 A·B, 고객 A·B | 교차 권한 차단 |
| E2E-07 | 공항→숙소, 숙소→숙소 노선 | 인계 장소·마감·용량 정확성 |
| E2E-08 | 결제 웹훅 중복·역순·미수신 | 수납·예약·환불 대사 |
| E2E-09 | 기사 재배차·QR 재스캔 | 이전 권한 종료·중복 이벤트 없음 |
| E2E-10 | 공항 인계 장소 변경·고객 지각 | 최신 안내·보관·지원 |
| E2E-11 | 3언어·2테마·키보드 | 입력 유지·접근성 |
| E2E-12 | 계정 삭제·자료 보존 | 세션 폐기·분리 보존·삭제 작업 |

테스트 데이터는 실제 호텔·개인·카드 정보를 가장하지 않는 합성 데이터로 만든다. 공급사 테스트 규칙이 실제 출금을 포함하는 경우 해당 사실과 취소 확인을 기록하며, 일반 자동화에서 실결제를 실행하지 않는다.

## 4. CI와 변경 검토

PR 기본 검사: 포맷/린트 → 타입 검사 → 관련 도메인·API 테스트 → DB 마이그레이션·RLS → 빌드 → 핵심 E2E. 필수 환경이 없으면 ‘미실행’을 명확히 기록하고 성공으로 통과시키지 않는다.

프리뷰 배포는 합성 데이터·test 모드만 사용한다. 비밀값 유출 검사, 의존성 취약점 검사, 번역 키 누락 검사, 비공개 경로 색인·캐시 검사 포함. 실패의 원인과 변경 범위를 확인해 필요한 검사만 다시 실행한다.

메인 오케스트레이션의 스크립트 이름은 A01에서 실제 구현한다. 명령이 없거나 도구 설치가 안 됐으면 그것을 제한으로 기록한다. 실행하지 않은 테스트 결과를 문서에 적지 않는다.

## 5. 배포 절차

1. 배포 대상 환경과 DB 프로젝트를 검증한다.
2. 추가형 DB 마이그레이션을 먼저 적용하고 이전 코드와 호환되는지 확인한다.
3. 기능 플래그를 닫은 상태로 앱을 배포한다.
4. 헬스체크·권한·예약 조회·결제 callback 경로를 검증한다.
5. 필요한 수하물 요금·정책·호텔·인계 장소 데이터를 입력한다.
6. 해당 기능 플래그를 점진적으로 연다.
7. 오류·미확정 결제·알림 실패·용량 충돌을 관찰한다.

롤백은 이전 앱 버전과 현재 DB의 호환성을 전제로 한다. 파괴적 DB 변경은 백업 복구·정정 마이그레이션 등 별도 절차를 갖춘다. 잘못된 배포를 되돌린다고 이미 발생한 결제·알림·인계가 되돌아가지 않는다.

## 6. 모니터링·작업 운영

모니터링 항목: API 오류·지연, 결제 pending/unknown 시간, 웹훅 검증 실패, outbox backlog, 환불 unknown, 사진 업로드 실패, 권한 거부 급증, 슬롯 충돌, 공항 준비 지연, 외부 알림 실패, 공급사 장애.

경보에는 requestId·주문 내부 참조·업무 유형을 포함하고 연락처·토큰·사진 URL을 제외한다. 운영자의 수동 재처리는 원래 멱등 작업을 재사용한다.

기술 상태와 사업 상태를 구분한다. 서버가 200을 반환해도 예약 확정이 실패했다면 정상 거래로 집계하지 않는다. 실시간 구독이 실패하면 제한된 polling으로 최근 상태를 조회할 수 있게 한다.

## 7. 백업·복구

Supabase DB 백업에는 Storage 파일 본문이 포함되지 않으므로 DB와 파일의 복구 계획을 분리한다. DB 백업/PITR 선택, 파일 별도 보존, 버전 관리, 삭제 대기 기간을 설정한다. 삭제된 인계 사진 복구가 필요한 경우 객체 보존 정책과 연결한다.

운영 목표 초안: 확정 거래 RPO 15분 이내, 핵심 주문 조회 RTO 4시간 이내를 목표로 검토한다. 이는 공급사 기본 보장이 아니며 선택한 백업·로그·복구 시험으로 달성 가능한 값을 확정한다. 구성 미완료 상태에서 목표 달성을 주장하지 않는다.

복구 시험: 격리된 프로젝트에 DB 복원 → 사진 참조 복구 → 사용자·권한 확인 → PG 기록과 주문 대사 → outbox 재처리 시 외부 중복 발송 차단 → 시험 결과 기록. 시험 환경에서는 실제 알림·결제를 비활성화한다.

## 8. PWA

설치 가능한 manifest·아이콘·색·기본 오프라인 안내를 제공한다. 서비스 워커는 공개 정적 자원과 허용된 예약증 사본만 캐시한다. 결제·인증·개인 API 응답을 범용 cache-first로 저장하지 않는다.

오프라인 예약증에는 마지막 확인 시각과 ‘최신 상태는 연결 후 확인’을 표시한다. 결제·최종 인계는 오프라인 완료 불가. 업데이트 알림은 결제 중 강제 새로고침하지 않고 안전한 시점에 적용한다. 브라우저별 설치·푸시 지원은 기기 검증 결과에 따라 안내한다.

## 9. 현장용 PWA (네이티브 앱 없음)

고객용·직원용 네이티브 앱은 만들지 않는다. 기사·호텔·운영자는 같은 웹앱의 `/driver`, `/partner`, `/admin`를 홈 화면에 설치해 사용한다. 한국 직원 기기는 구글·애플 서비스가 정상 동작하므로 웹 푸시를 사용할 수 있다.

브라우저 기능으로 구현할 현장 기능:

- 카메라 QR 스캔(getUserMedia + 디코더)과 사진 촬영·압축 업로드.
- 오프라인 작업 큐(IndexedDB): 스캔·사진은 임시 저장, 최종 인계는 서버 확인 후 확정.
- 웹 푸시와 화면 내 알림함. iOS는 홈 화면 설치 후에만 웹 푸시가 오므로 설치 안내를 제공한다.
- 작업 화면이 열린 동안의 위치. 백그라운드 연속 위치는 차량 GPS 단말 연동으로 대체한다.

카메라·위치·알림 권한은 필요한 시점에 목적을 설명하고 요청한다. 거부해도 코드 직접 입력·파일 선택·수동 확인 대안을 제공한다. 네이티브 앱은 현장 기기 검증에서 PWA로 해결되지 않는 문제가 기록될 때만 재검토한다.

## 10. 결제 채널과 심사

수하물 배송은 앱 밖에서 제공하는 실물 서비스이므로 위챗페이·알리페이·카드 PG를 사용한다. 미니프로그램 결제는 위챗페이 크로스보더 가맹과 AppID 연결 후 실기기로 검증하고 심사 결과를 별도로 기록한다.

## 11. WeChat Mini Program

[04 문서 8절](04-architecture-integrations.md)의 하이브리드 구조를 따른다. 예약·주문·예약증·지원은 `web-view`로 웹을 재사용하고, 위챗 로그인·위챗페이(`wx.requestPayment`)·구독 메시지 동의는 미니프로그램 네이티브 페이지로 구현한다. 기능 없는 웹 감싸기만으로는 심사 반려 위험이 있으므로 위 네이티브 기능이 동작해야 완성으로 본다. 공통 서버의 상태 규칙을 재사용한다.

등록 경로: 위챗 공식 플랫폼에서 해외 법인(한국 사업자)으로 미니프로그램 계정 개설 → 주체 인증 → 업종 선택 → AppID로 개발·업무 도메인 인증 → 결제 대행사를 통한 위챗페이 크로스보더 가맹 후 AppID 연결 → 심사·출시. 해외 법인 계정은 중국 본토 미니프로그램 备案 대상이 아니므로 검색 노출·기능 제한 여부를 신청 시점에 확인한다. 계정·결제 권한 준비는 웹 개발과 병행한다.

확인·설정 항목: 운영 주체, appid, 업종·서비스 범주, 서버 도메인, 개인정보 안내, 미니프로그램 결제 권한, 상점 연결, 콜백 검증, 구독 메시지 지원, 업로드 제한, 출시 심사 자료. 사용자 결정에 따라 계약·자격은 준비됐다고 가정하되 실제 설정값과 계정 권한은 연동 테스트로 확인한다.

WeChat code 교환은 서버에서 수행하고 app secret을 클라이언트에 넣지 않는다. 플랫폼별 openid를 글로벌 계정 ID로 그대로 사용하지 않는다. unionid가 항상 제공된다고 가정하지 않고 명시적 계정 연결 절차를 제공한다. 로그인·결제 채널 변경으로 새 중복 주문이 생기지 않게 한다.

## 12. 네트워크·기기 검증표

| 환경 | 최소 확인 |
|---|---|
| 중국 본토 Wi-Fi·모바일 | DNS·첫 화면·호텔 검색·사진·결제·복귀·재조회 |
| 제주 Wi-Fi·한국 유심 | 같은 예약 완주·현장 QR |
| 중국 유심 로밍 | 라우팅 차이·알림·결제 앱 복귀 |
| WeChat iOS·Android 웹뷰 | 쿠키·파일 선택·PG 호출·뒤로 가기 |
| Safari·Android 주요 브라우저 | 세션·카메라·PWA·공유 |
| 현장용 PWA(iOS·Android 설치) | 카메라·권한 거부·오프라인 큐·웹 푸시·화면 잠금 복귀 |
| 미니프로그램 실제 계정 | 로그인·결제·구독 알림·배포 버전 |

각 항목에 기기·OS·앱 버전·네트워크·날짜·결과·증거를 기록한다. 중국 접속을 직접 시험하지 않았다면 ‘미검증’으로 둔다. 시뮬레이터 성공을 실제 중국망 성공으로 대체하지 않는다.

## 13. 성능·보안 목표

성능 초안: 핵심 랜딩의 LCP p75 2.5초 이하, CLS 0.1 이하, 내부 조회 API p95 1초 이하를 목표로 측정한다. 외부 결제·중국망은 별도 분포로 보고한다. 이 값은 제품 목표이며 실측 전 성능 주장으로 쓰지 않는다.

사진은 업로드 전 크기 조절, 서버 검증, 썸네일을 제공한다. API 페이지네이션과 인덱스를 검증한다. 상태 조회 polling은 backoff·가시성 제어를 적용한다. 로그·추적 도구에서 비밀값이 마스킹되는지 시험한다.

출시 핵심 보안: 다른 주문 접근, 임의 역할 상승, Storage 우회, 가격 변조, webhook 위조, 복구 링크 재사용, 수령 코드 대입, 쿠폰 악용, 파일 위장, CSRF, 공개 캐시에 개인정보 노출을 테스트한다.

## 14. 단계별 배포 판정

| 단계 | 필요한 증거 |
|---|---|
| A | 수하물 IA·중국어 기본 화면·테마·기본 권한·빌드, 360px 모바일 뷰포트 E2E 기본 실행, 실행 환경 감지(일반/위챗 브라우저/미니프로그램 web-view)·토큰 세션 테스트, 고객 화면 구글 도메인 호출 0건 검사 |
