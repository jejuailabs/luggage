# 07. 수하물 물류·위치추적·현장 운영

연결: [메인](../AGENTS.md), [데이터](05-data-auth-security.md), [결제](06-booking-payments-settlement.md)

## 1. 운영 데이터를 제품으로 표현

운송 자격·보험·공항 인계 조건은 준비된 것으로 가정한다. 실제 허용된 장소·시간·연락처·보상정책을 관리자가 입력하면 적용되게 만든다. ‘공항 근처’처럼 불명확한 자유문구만으로 인계 장소를 관리하지 않는다.

장소 데이터: location_id, 장소 유형, 한국어 원명, 언어별 설명, 주소·좌표, 현장 사진, 출구·층·랜드마크, 운영시간, 차량 접근 조건, 담당 채널, 유효기간. 공항 인계 장소 변경은 기존 예약 안내 재발송과 연결한다.

노선 설정: 서비스 방향, 출발 권역, 도착 권역, 수거 마감, 인계 예정 범위, 항공편 대비 안전 여유, 적재 단위, 최대 작업 수, 당일 접수 허용 여부. 날씨·휴무·차량 장애로 특정 날짜의 판매를 닫을 수 있다.

## 2. 개별 짐과 주문 상태

개별 bag 상태:

```text
registered → at_origin → collected → in_transit → ready_for_handoff → delivered
                  ↘ exception_hold ↗
collected/in_transit/ready_for_handoff → return_in_progress → returned
registered/at_origin → cancelled_before_pickup
```

`exception_hold`에는 이전 상태와 이유를 저장하고 해소 후 허용 상태로 복귀한다. ‘분실 조사 중’을 delivered로 처리하지 않는다. 정정은 기존 이벤트 수정 대신 반대·정정 이벤트와 사유를 추가한다.

배송 작업 상태: planned, assigned, picking_up, transporting, ready, completed, exception, returning, returned, cancelled. 주문 전체 완료는 취소된 짐을 제외한 모든 대상 짐의 유효 인계 결과로 계산한다. 3개 중 2개 인계는 ‘2/3개 인계’로 표시한다.

## 3. QR 태그·수령 코드

태그 QR은 무작위 tag_id 또는 서명된 태그 식별값만 담는다. 이름·전화·숙소·주문 접근권한·수령 비밀코드를 담지 않는다. QR을 공개적으로 촬영해도 고객 개인정보를 읽을 수 없어야 한다.

기사·호텔의 스캔은 인증된 앱에서 배정·파트너 관계를 확인한 후 이벤트를 생성한다. 예상하지 않은 태그는 ‘다른 작업의 짐’으로 경고하고 임의로 현재 주문에 붙이지 않는다. 태그 재발급은 구 태그 폐기·신 태그 연결·사유를 감사 기록으로 남긴다.

고객 수령 코드는 태그와 별개다. 짧은 만료시간·시도 제한·재발급·원자적 소비를 적용한다. 코드를 검증한 다음 해당 짐 목록을 대조하고 최종 인계를 기록한다. 한 주문의 일부만 전달할 수 있으므로 challenge에 대상 bag_ids와 작업 버전을 연결한다.

## 4. 인계 이벤트 계약

| 이벤트 | 수행자 | 필수 증빙·검증 |
|---|---|---|
| origin_received | 호텔/고객 확인 후 운영자 | 짐 개수, 위치, 태그 연결 |
| collected | 배정 기사 | QR, 수량, 외관 상태, 사진 또는 승인된 예외 사유 |
| loaded | 배정 기사 | 차량·노선, 적재된 짐 목록 |
| arrived | 배정 기사 | 목적지, 도착 시각 |
| ready_for_handoff | 기사/인계 담당 | 실제 수령 가능한 위치·시간 |
| delivered | 배정 인계 담당 | 고객 challenge 검증, 대상 짐 대조 |
| returned | 배정 담당 | 반환 수령자 확인, 증빙 |
| correction | 권한 있는 운영자 | 원 이벤트, 정정 이유, 변경 전후 |

이벤트는 client_event_id, bag_id, actor_id, job_id, route_id, event_type, device_occurred_at, server_received_at, expected_version, evidence_refs를 가진다. 기기 시각은 참고이며 마감 판단·금융 규칙은 서버 시각 기준이다.

## 5. 배차와 적재

초기 배차는 운영자 수동 배정+권역·시간·용량 검증으로 시작한다. 고객 시간 창, 차량 적재량, 기사 근무 가능, 공항 인계 기한, 호텔 운영시간을 제약으로 모델링한다. 차량 한 대의 단순 최단거리만으로 배차 성공을 판정하지 않는다.

추천 배차 기능을 추가할 때도 변경 전 경로·예상 소요·미충족 제약을 보여주고 운영자가 확정한다. 실제 도로 시간 API가 없으면 ‘추정’으로 표시한다.

재배차는 새 담당자 권한 부여·이전 담당자 권한 종료·작업 상태·알림을 함께 처리한다. 수거된 짐을 다른 차량으로 옮길 때 기사 간 인계 이벤트를 남긴다. 배정만 바뀌었다고 물리적 소지자가 바뀐 것으로 처리하지 않는다.

## 6. 위치추적의 단계

| 단계 | 데이터 | 고객 표시 | 제한 |
|---|---|---|---|
| 초기 | QR·인계 사진·업무 이벤트 | 호텔 수거, 운송 중, 공항 준비 | 실시간 GPS라는 표현 금지 |
| 차량 추적 | 근무 중 차량/기사 기기의 위치 | 배송 차량의 최근 위치·갱신시각 | 짐 자체 GPS 아님 |
| 개별 장치 | 검증된 태그 API의 위치·배터리·관측시각 | 해당 장치의 마지막 관측 | 기기·망·비용·정확도 실측 필요 |

125원 태그를 독립 GPS 장치로 확정하지 않는다. QR·NFC·Bluetooth·GPS+통신 모듈은 다른 기술이다. 실제 장치를 선정할 때 API 접근, 전원, 통신망, 해외 인증·반입, 갱신 간격, 실내 수신, 배터리, 분실시 개인정보를 검증한다.

차량 위치 수집은 업무 활성 상태에서만 수행한다. 기사 화면은 PWA이므로 백그라운드 연속 수집을 보장하지 않는다. 차량 추적은 차량 GPS 단말·관제 서비스를 Tracking 어댑터로 연동하는 것을 우선하고, 보조로 작업 화면이 열린 동안의 기사 기기 위치를 쓴다. 기사에게 수집 상태를 표시한다.

마지막 위치가 오래됐으면 stale로 표시하고 움직이는 애니메이션을 만들어 실시간처럼 보이지 않는다. 완료 후 고객의 위치 구독 권한을 종료한다.

## 7. 오프라인 작업

기사 화면은 배정 목록·필요 최소 인계 정보를 제한된 기기 저장소에 보관할 수 있다. 로그아웃·배정 해제·보존 만료 시 제거한다. 사진·스캔은 pending_sync 상태로 저장하고 네트워크 복구 시 동일 client_event_id로 재전송한다.

오프라인 스캔을 서버 확정과 구분한다. 새 배정·상태 충돌은 서버가 판단해 재검토 큐에 둔다. 고객 challenge 검증과 최종 수령 완료는 온라인을 원칙으로 한다. 긴급 수동 인계는 운영자 예외 기록·수령 증빙을 남기고 연결 복구 후 확정한다. 네트워크가 없는데 화면에 확정 완료를 표시하지 않는다.

## 8. 사고·예외 처리

| 상황 | 제품 동작 | 완료 조건 |
|---|---|---|
| 호텔에서 짐을 찾지 못함 | missing_at_origin, 고객·호텔 연락, 수거 보류 | 실제 수거 또는 명시적 취소 |
| 외관 손상 발견 | 수거 전 사진·고객 확인·incident | 인수 조건 기록 |
| 등록과 실제 수량 다름 | 차이 표시·추가 견적/인계 수정 | 고객 승인·용량 확인 |
| 차량 고장 | 미인계 짐 목록·대체 차량·기사 간 인계 | 모든 짐의 소지자 추적 |
| 도착 지연 | 약속 기한 대비 경보·지원 연락 | 실제 상태·대안 전달 |
| 항공편 변경 | 새 시각·가능 인계창 재계산 | 고객 확인·작업 반영 |
| 고객 미도착 | 대기 기한·안내·후속 보관 | 실제 인계 또는 반환 |
| 짐 일부 누락 | 주문 전체 완료 방지·조사 | 누락 짐 해결·보상 별도 |
| 분실·보상 요청 | 증빙 잠금·담당자·보험 참조 | 책임 판단·환불/보상 기록 |
| 공항 인계 장소 변경 | 주문별 안내 버전·알림 재발송 | 고객에게 최신 안내 제공 |

분실·파손 보상은 PG 주문 환불과 별도 claim으로 추적한다. 보상 합의가 완료됐다고 실제 결제 환불도 완료된 것으로 표시하지 않는다.

## 9. 알림과 고객지원

이벤트별 알림: 예약 확정, 사진 미등록, 수거 완료, 인계 준비, 지연, 장소 변경, 수령 완료, 취소·환불 결과. 메시지는 주문 당시 언어로 생성하며 중요 약속 문구는 승인된 템플릿을 사용한다.

발송·수신·읽음 상태는 공급사가 실제 제공하는 범위만 표시한다. 외부 메신저 발송 실패 시 웹 내 알림과 운영자 후속 작업을 만든다. 자동으로 고객에게 전달됐다고 추정하지 않는다.

지원 화면은 주문 맥락, 현재 소지자, 마지막 이벤트, 고객 언어, 이전 문의를 보여준다. 내부 메모와 고객 메시지를 시각적으로 분리해 오발송을 방지한다. 운영시간·긴급 연락 경로는 설정값으로 관리한다.

## 10. 운영 대시보드

오늘 확정 주문, 미수거, 공항 준비 지연, 고객 대기, 부분 인계, 미해결 사고, 알림 실패를 우선순위로 표시한다. 지도는 보조이며 목록만으로도 운영 가능해야 한다.

지표는 준비 정시성/실제 인계 정시성, 기사·호텔별 누락, 사진·태그 증빙률, 노선 적재율, 평균 지원 처리시간을 분리한다. 표본 수·기간·시간대를 같이 보여준다.

## 11. 수용 기준

- LOG-01: 서로 다른 주문의 태그를 스캔하면 상태 변경 불가.
- LOG-02: 3개 중 2개 전달시 전체 completed 불가.
- LOG-03: 같은 스캔을 재전송해도 이벤트·알림이 중복되지 않음.
- LOG-04: 재배차 후 이전 기사의 변경 권한 종료.
- LOG-05: 차량 위치가 끊기면 stale 표시, 임의 경로 재생 없음.
- LOG-06: 결제 환불 뒤에도 수거된 짐의 반환 작업 유지.
- LOG-07: 사진 URL·QR·고객 공유 링크에서 다른 주문 정보 접근 불가.
- LOG-08: 인계 코드 동시 검증에도 같은 대상 인계가 한 번만 완료.
- LOG-09: 기기 시각이 틀려도 서버 마감·이벤트 정합성 유지.
