# 06. 수하물 예약·가격·결제·환불·호텔 정산

연결: [메인](../AGENTS.md), [데이터](05-data-auth-security.md), [현장](07-logistics-tracking-operations.md)

## 1. 판매 가능한 수하물 노선

`hotel_to_airport`, `airport_to_hotel`, `hotel_to_hotel` 세 가지 방향을 지원한다. 초기 주요 흐름은 숙소→공항이다. 판매 여부·지점·권역·날짜·수거 및 수령 창·차량 용량은 관리자가 설정한다.

항공편 출발시각과 공항 인계 약속 사이의 안전 여유, 호텔 운영시간, 당일 마감, 대형짐 적재 가능 여부를 서버가 확인한다. 유효하지 않은 조합의 가격을 먼저 받고 나중에 취소하는 흐름을 기본으로 두지 않는다.

## 2. 견적 계약

입력: 방향, 출발/도착 location ID, 서비스 날짜, 선택 슬롯, 항공편명·출발시각, 짐 규격별 수량, 옵션, 쿠폰·호텔 제휴 코드. 항공편 정보는 인계 가능성 확인에 쓰며 정책 없이 임의 할증하지 않는다.

계산 순서:

1. 출발/도착 지점·판매 권역·이용일·마감 확인.
2. 짐 규격·수량과 슬롯의 공간·작업 용량 확인.
3. 적용일이 맞는 요금표·옵션·할인 규칙 사용.
4. 세금·총액·환불 배분값을 서버에서 정수로 계산.
5. 견적 ID, 가격 규칙 버전, 항목, 총액, 만료시각 반환.

실제 판매 요금은 관리 설정값이다. 예시 데이터는 시드·테스트 전용임을 표시한다. 주문 확정 뒤 요금표가 바뀌어도 고객의 당시 가격·정책 스냅샷을 보존한다. 실제 청구 통화와 화면의 참고 환산액을 구분한다.

## 3. 슬롯 홀드와 동시성

수용량은 `held_units + committed_units <= max_units`를 DB 트랜잭션에서 지킨다. 보통짐·대형짐의 점유 단위는 운영 설정으로 관리한다. 필요한 bucket을 고정 순서로 잠그고 하나라도 부족하면 전체 주문을 만들지 않는다.

주문 생성은 견적 소유권·만료·입력 해시→슬롯 재검사→홀드→주문·수하물 행→outbox/멱등 결과 저장 순서다. 같은 Idempotency-Key와 본문이면 같은 주문을 돌려주고, 같은 키·다른 본문은 409를 반환한다.

홀드 만료는 설정으로 관리하며 초기 테스트 시드에서는 10분을 사용한다. 결제 결과가 미확인인 주문은 대사 작업으로 확인한다. 홀드 만료 후 결제 성공이 늦게 확인되면 용량을 다시 원자적으로 확보한다. 실패하면 `needs_review`와 환불/대안 처리 작업을 만든다. 과예약을 감추고 confirmed로 표시하지 않는다.

## 4. 상태 정의

| 도메인 | 상태 | 중요한 규칙 |
|---|---|---|
| 예약 | draft, held, confirmed, cancelled, expired, needs_review | held→confirmed는 결제·용량 검증 후 |
| 결제 시도 | created, pending, succeeded, failed, cancelled, unknown | timeout은 unknown |
| 결제 요약 | unpaid, pending, paid, partially_refunded, refunded | 수납·환불 기록에서 계산 |
| 환불 요청 | requested, approved, rejected | 승인과 실제 환불 구분 |
| 환불 실행 | queued, processing, succeeded, failed, unknown | PG 재조회 후 성공 확정 |
| 호텔 수수료 | pending, eligible, batched, paid, reversed | 배송·환불과 연결 |

배송 상태는 [07](07-logistics-tracking-operations.md)을 따른다. 예약 취소·환불 후에도 이미 수거한 짐의 반환 작업은 유지한다.

## 5. 결제 확정

서버가 확정 견적 금액·통화·주문 ID로 결제 세션을 만든다. 고객이 결제창에서 돌아오면 화면은 ‘결제 확인 중’으로 시작한다. PG 웹훅은 공급사별 원문·서명·시간 기준을 검증하고 중복 이벤트를 기록한다. 서버가 PG 거래를 조회해 상점·외부거래 ID·금액·통화·성공 여부를 주문과 대조한 뒤 예약을 confirmed로 바꾸고 용량을 commit한다.

브라우저의 `paid=true`나 성공 URL은 근거가 아니다. 결제 중 창을 닫아도 웹훅·주기적 대사로 결과를 찾을 수 있어야 한다. 이벤트 수신 중 외부 조회가 오래 걸리면 이벤트를 영속 저장한 뒤 재시도 가능한 작업으로 처리한다.

| 예외 | 처리 |
|---|---|
| 웹훅 중복 | provider+event_id unique, 중복 원장·알림 없음 |
| 이벤트 역순 | 공급사 현재 상태 재조회, 성공을 늦은 실패로 덮지 않음 |
| PG 호출 timeout | 동일 상점 주문 ID 조회 후 재시도 |
| 두 결제창 성공 | 초과 수납 조사·환불 작업, 예약 1회 확정 |
| 금액·통화 불일치 | 확정 중지·금융 검토 큐 |
| 성공 후 슬롯 용량 없음 | needs_review·고객 안내·대안/환불 |
| 고객 브라우저 종료 | 서버 대사 후 주문 재조회에서 예약증 제공 |

## 6. 결제 채널

한국 사업자용 PG 어댑터에서 해외 카드, Alipay, WeChat Pay를 결제 환경별 capability로 관리한다. H5 웹, 위챗 내부 웹뷰, 미니프로그램, iOS·Android 앱의 지원 여부를 별도로 설정한다. 계약 완료를 개발 전제로 삼지만, 실제 계정·MID·수수료·환불 기능은 공급사 테스트 결과로 확정한다.

로컬·프리뷰에서는 mock, 검증 환경에서는 sandbox, 운영에서는 확인된 live만 제공한다. mock 성공을 운영 결제 성공으로 기록하지 않는다. 결제 서비스 장애 시에는 확인 중·재시도·지원 흐름을 제공하고 허위 예약 확정을 만들지 않는다.

## 7. 변경·취소·부분환불

취소 가능 여부와 예상 환불액은 주문 당시 취소 정책 버전, 한국 시간 기준 마감, 짐 수거 상태로 계산한다. 실제 규정·보험 범위는 운영 설정값을 사용한다. 수거 전 고객 취소와 수거 후 반송이 필요한 취소를 분리한다.

결제 전 짐 개수·슬롯 변경은 재견적. 결제 후 변경은 새 용량 확보→차액 결제 또는 환불→기존 용량 해제 순으로 처리한다. 목적지 변경은 배차·운송 가능성 검토를 거친다.

부분환불은 짐별 원가격·할인·세금 배분 스냅샷을 사용한다. 반올림 잔여 배분 규칙을 고정한다. 같은 주문의 누적 성공·처리 중 환불액이 실제 수납액을 넘지 않게 결제 행 잠금과 제한된 서버 명령을 사용한다. 환불 timeout에서는 새 환불 ID를 무조건 생성하지 않고 기존 거래를 재조회한다.

고객에게 ‘취소 요청’, ‘환불 승인’, ‘PG 환불 완료’를 구분해 표시한다. 취소로 수하물 인계·사고 기록을 삭제하지 않는다.

## 8. 호텔 제휴·정산

호텔 QR·제휴 코드는 주문 생성 때 귀속을 확정한다. 결제 후 URL 변경만으로 수수료 수취인을 바꾸지 않는다. 계약별 정액/비율, 적용 기준, 반올림, 확정 조건, 환불 조정 규칙을 스냅샷으로 저장한다.

배송 완료 후 적격 원장 항목 → 정산 초안 → 검토 → 확정 → 지급 기록/연동 → 대사 순으로 처리한다. 초기에는 내역서·지급 증빙까지 제공하고 자동 송금은 검증된 공급사 연동을 별도 활성화한다. 지급 후 환불이 생기면 과거 기록을 수정하지 않고 차기 상계 또는 환수 원장을 만든다.

호텔 직원은 자기 호텔의 주문 실적·정산 내역만 조회한다. 수수료 규칙·계좌 변경은 금융 담당 권한과 감사 로그가 필요하다.

## 9. 검증

- 마지막 슬롯 동시 주문에서 허용 수량만 확정.
- 동일 결제 웹훅 10회에도 예약·원장·알림 1회.
- 결제 성공 후 탭 종료·다른 기기 복구 시 주문 유지.
- 늦은 결제는 재확보 또는 needs_review, 과예약 없음.
- 동시 부분환불 총액이 수납액을 넘지 않음.
- 쿠폰·가격·통화 클라이언트 조작을 서버가 거부.
- 수거 후 취소에도 실제 짐 반환 업무가 남음.
- mock/sandbox/live 결과가 서로 다른 상태로 기록.
